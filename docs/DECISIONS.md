# Decisions

One line each. **[H]** marks decisions a human should confirm.

- D1. `make` comes from winget `ezwinports.make` (approved by user). It's a local dev tool, not a shipped dependency.
- D2. Licenses: LGPL is allowed for unmodified, dynamically linked backend Python packages (for example psycopg). Added to the allowlist: 0BSD, CC0-1.0, Unlicense, BlueOak-1.0.0, CC-BY-4.0 (data only, for example caniuse-lite), HPND (Pillow), Python-2.0. Frontend bundles stay strict. GPL, AGPL, SSPL and BUSL stay banned (approved by user). Confirmed in Run 2.
- D3. Dev runs in Docker (user keeps Docker Desktop running). Containers use Python 3.12. The host's Python 3.13 is not used for the app.
- D4. Django project package is `backend/config/`. Apps sit at `backend/<app>/`: core, labs, projects, documents, provenance, ethics, audit.
- D5. Python dependencies are pinned in `backend/requirements.txt` and `requirements-dev.txt` (plain pip, no extra tooling).
- D6. The SPA uses allauth headless with session cookies and CSRF. The Vite dev server proxies `/api` and `/_allauth` to the backend so it all stays same-origin.
- D7. Primary keys are UUIDs, so object IDs can't be enumerated across labs.
- D8. Passwords use Argon2 (argon2-cffi), with Django defaults as the fallback.
- D9. Background jobs: Celery worker plus Celery beat, both on Valkey.
- D10. BlockNote UI package: `@blocknote/shadcn`, to match shadcn/ui.
- D11. Edit conflicts: a Document has an integer `version`. A save must send its base version, and a stale save gets HTTP 409.
- D12. Placeholder product name "Research Workspace", kept in one constant. Accent colour indigo. Confirmed in Run 2.
- D13. Lineage graph layout uses fixed columns by type (dataset, analysis, result, manuscript), with no layout library.
- D14. Dev email goes to the console backend.
- D15. Settings fall back to SQLite when `POSTGRES_HOST` is unset, so agents can check quickly on the host. `make test` always runs against Postgres in Docker.
- D16. Custom user model `core.User` (AbstractUser, UUID pk, unique email, no username, `USERNAME_FIELD="email"`), created in Phase 0 so migrations never need rebasing.
- D17. Celery talks to Valkey through the `redis` Python client (MIT) with `redis://valkey:6379/0` URLs. Valkey is the server.
- D18. Lab-scoped default manager raises `UnscopedQueryError` on evaluation unless scoped via `.for_lab()` or `.visible_to()`. `Model.unscoped` is allowed only in tenancy, permissions, admin and migrations, and a grep test enforces that.
- D19. Project access requires a ProjectMembership. pi and lab_admin are implicit leads of every project, and a lab viewer's project role is capped at viewer.
- D20. Provenance objects belong to exactly one project and links can't cross projects. A new dataset version is a new DatasetRecord row.
- D21. Anonymous gets 401. Another lab or an invisible object gets 404, so existence doesn't leak. A visible object with a forbidden action gets 403.
- D22. URLs: `/api/labs/<lab_id>/projects/<project_id>/<collection>/` for list and create, flat `/api/labs/<lab_id>/<collection>/<model>_id/` for items, so each URL has at most one parent to check.
- D23. AuditEvent is append-only: model and queryset guards, a Postgres trigger that rejects UPDATE, DELETE and TRUNCATE, and INSERT/SELECT-only DB grants in prod.
- D24. Users are deactivated, never deleted, and user FKs PROTECT. Projects and documents soft-delete via `deleted_at`, and nothing is purged automatically.
- D25. Email verification is mandatory. Accepting an invite requires the invite email to match **any** verified email on the logged-in account, not only the primary one (users can add and verify extra addresses in account settings), so a forwarded link still can't be used by someone else. Confirmed in Run 2, with the any-verified-email change.
- D26. Downloads stream through Django, with no presigned or public URLs this run. Storage key: `labs/<lab_id>/attachments/<attachment_id>`.
- D27. Ethics approvals are lab-level: every lab role can read them, and pi, lab_admin and member can edit them. Confirmed in Run 2.
- D28. delete_project is pi and lab_admin only, and is a soft delete. export is pi, lab_admin or project lead. Every export writes an audit event, and the lab PIs get an in-app notification when anyone else exports. Confirmed in Run 2.
- D29. Ethics reminders send only the tightest threshold crossed (60, 30 or 7 days), deduped per approval, threshold and expiry date, so a missed job run still catches up.
- D30. Notifications are lab-scoped (`/api/labs/<lab_id>/notifications/`), so they reuse the same tenancy path.
- D31. Each child's lab must match its parent's, enforced in `save()`, an `m2m_changed` receiver and services. Composite DB FKs and M2M triggers now back this up (`core/lab_db.py`, ARCHITECTURE section 1).
- D32. The permission matrix holds hand-written expected status codes per persona, never derived from the role tables, so it independently checks them.
- D33. Lab model serializers drop DRF auto-unique validators, which would run unscoped queries. DB constraints enforce uniqueness and an IntegrityError becomes a 400.
- D34. MIT-0 is on the allowlist. Vitest is back on jsdom and cffi is no longer pinned. Confirmed in Run 2.
- D35. Phase 1 JSON contract. Lists are plain arrays (no pagination) until a list needs it. Audit events get cursor pagination in Phase 2. Shapes:
  - User `{id,email,display_name}`.
  - Lab `{id,name,institution:{id,name},my_role,my_permissions:[str]}`, where `my_permissions` comes from core.permissions.
  - Membership `{id,user:User,role,created_at}`.
  - Invite `{id,email,role,expires_at,created_at,invited_by:User}`.
  - Invite preview `{lab_name,role,email}`.
  - Invite accept returns a Lab.
  - Errors use DRF's `{detail}` or field errors.

- D37. Email links use the `FRONTEND_URL` env var: invites go to `/invite/<token>` and email verification to `/account/verify-email/<key>`.
- D38. An Attachment has exactly one owner: a project, or (Phase 5) an ethics approval. A DB check constraint enforces it. Each lab-data model declares its permission domain explicitly. `_resolve` never infers "lab-level" from a null FK, and an unresolvable owner is denied (fail closed). From security review #4.
- D39. Soft-deleted projects and their children are invisible to every permission check (`project_role`, `can`, `require`, `users_with`), not only to listings. From review #1.
- D40. Accepting an invite re-checks that the inviter can still `manage_members` and grant that role. Removing or demoting a member revokes the open invites they sent. From review #2.
- D41. Settings fail closed: DEBUG defaults to False, and startup refuses a missing or placeholder SECRET_KEY when DEBUG is off. `/admin/` is mounted only when DEBUG is on. CACHES uses Valkey (Django's built-in RedisCache). Invite creation is throttled. From review #3, #6, #8.
- D42. Documents use explicit save (Save button, Ctrl/Cmd+S), not autosave, so revisions stay meaningful. A stale save shows a conflict dialog and never overwrites silently.
- D43. The project tabs are Overview, Tasks, Documents, Files, Research and Lineage. Research has sub-tabs for Datasets, Analyses, Results, Decisions and Manuscripts. Record routes are `/labs/:labId/projects/:projectId/research/<datasets|analyses|results|decisions|manuscripts>/:id`.
- D44. Clicking a node in the lineage view opens a panel showing its whole upstream chain. A result shows its analysis (repo@commit) and that analysis's dataset versions. A manuscript shows its results, each with that chain. So tracing goes lab â†’ project â†’ Lineage tab â†’ manuscript or result node, then read the panel: within the three-click limit. - D45. The command palette searches the lab's projects plus the current project's documents and research records. A lab-wide search endpoint is deferred.
- D46. Seed data comes from `manage.py seed_pilot` (`make seed`). It only runs when DEBUG is on, it's idempotent, it uses `@example.test` emails with pre-verified addresses, and the dev password is printed on the console.
- D47. Playwright end-to-end tests live in `frontend/e2e/` and run with `make e2e` against the running, seeded dev stack (`make dev` and `make seed` first). They stay out of `make test` so it doesn't need a live stack.
- D48. Ethics approvals (Phase 5): serialized `projects` are filtered through `visible_projects`. Linking or unlinking a project needs `edit_content` on that project. Approval files need `view_ethics` and visibility of at least one linked project, or that the user is a pi or lab_admin. From Phase 4 review #3.
- D49. Views and serializers resolve lab data through `visible_to()`. `for_lab()` is allowed only in services (whose lookups must also filter by an already-authorised project), jobs, permissions, tenancy and seeds, and a lint test enforces it. A placeholder SECRET_KEY is never used, whatever DEBUG is: in DEBUG the settings generate a random dev key and persist it in the git-ignored `backend/.dev_secret_key`, and outside DEBUG they refuse to start. From review #4 and #9.
- D50. `ran_by`, `decided_by` and `controlled_by` default to the actor. Naming someone else needs `edit_project` (project leads). Lab creation is throttled per user, and invites are capped per lab per day. Upload bodies over the limit are rejected from Content-Length before they're read, and uploads are throttled. From review #5, #6 and #8.
- D51. Expiry reminders and retention notices also go to lab admins, because they act as leads on every project (D19) and hold `view_retention`. Confirmed in Run 2.
- D52. Editing or deleting an ethics approval needs `edit_ethics` plus visibility of every linked project, unless the user is a pi or lab_admin. Approvals are soft-deleted, and their attachments are never cascade-deleted (the FK uses PROTECT, and the attachments are soft-deleted with the approval). From Phase 5 review #1.
- D53. Upload size is enforced while streaming, by a custom upload handler that aborts past `ATTACHMENT_MAX_BYTES`, so it doesn't depend on Content-Length alone. In production the reverse proxy must also cap the body size (see HANDOFF). From review #2.
- D54. `visible_to()` applies per-model row filters for lab-wide records: Notification shows only the recipient's own, and Invite needs `manage_members`. ## Run 2

- D58. Parallel test runs set `TEST_DB_NAME` (settings `DATABASES.TEST.NAME`), so concurrent `pytest` runs don't share one Postgres test database.
- D59. All new Run 2 audit actions and notification kinds were added up front in one migration each (`audit/0007`, `core/0005`), so parallel work doesn't produce conflicting migrations.
- D60. New backend dependencies: `django-allauth[socialaccount]` (pulls in `requests` and `PyJWT`), `django-anymail` (BSD-3-Clause) and `cryptography` (Apache-2.0 or BSD), pinned explicitly. All outbound HTTP uses `requests`.
- D61. The email send log is a structured log line on the `core.email` logger (recipient, template, status, attempt), not a database table. The email body is never logged or stored.
- D62. **[H]** Google sign-in links to an existing account only when Google says the email is verified and it equals (case-insensitive) a verified address of that account; otherwise it creates a new account. When it can't create one because the address is already on an account (Google's copy unverified, or the local copy unverified, including someone's unverified secondary address), nothing is created or linked and no password is wiped. allauth's enumeration-safe path runs instead: the SPA gets the pending `verify_email` stage, just like an email signup for a taken address, and the address gets allauth's "account already exists" email. The account owner can sign in with their password, verify the address, and then use Google or connect it from account settings. Known limit: an unverified address someone else added still blocks a Google signup for that address, the same as it already blocks email signup. Pruning stale unverified addresses would fix that.
- D63. Integration tokens are encrypted at rest with `MultiFernet` over `INTEGRATION_ENCRYPTION_KEYS` (comma-separated, newest first), held only as ciphertext in `editable=False` fields, and decrypted only by `access_token()` / `refresh_token()`. Outside DEBUG startup refuses without keys. In DEBUG a random dev key comes from the git-ignored `backend/.dev_integration_key` (D49 pattern). Rotation: prepend a key, run `manage.py rotate_integration_keys`, then drop the old key. A refused refresh, a disconnect or a revoke wipes the tokens. ARCHITECTURE section 9.
- D64. **[H]** Google Drive uses scope `drive.file` only (per-file access via the Google Picker), reads metadata only, and never downloads or exports contents. The Drive identity comes from `about.user` (`permissionId`, `emailAddress`), so no `openid`/`email` scope is requested. A broader scope (for example `drive.readonly`) needs a new decision and Google verification.
- D65. One OAuth callback for every integration provider: `/api/integrations/oauth/callback/`, under `/api/` so the Vite proxy covers it. Local redirect URI: `http://localhost:5173/api/integrations/oauth/callback/` (`FRONTEND_URL` + path, `settings.INTEGRATION_OAUTH_REDIRECT_URI`). The state lives in the server-side session, bound to user, lab and provider, single-use, 10 minutes, at most 5 pending. PKCE is S256. The provider is taken from the stored state, never from the callback.
- D66. **[H]** Integrations use their own Google OAuth client (`GOOGLE_DRIVE_CLIENT_ID` / `GOOGLE_DRIVE_CLIENT_SECRET`, `settings.INTEGRATION_CLIENTS`), separate from the sign-in client, so `include_granted_scopes` never merges sign-in scopes into a Drive grant. The same values may be reused if the human prefers one client; then both redirect URIs must be registered on it. Each connect sends `access_type=offline` and `prompt=consent`, so a refresh token is always issued.
- D67. The integrations HTTP client (`integrations/http.py`) is the only outbound path. It sends HTTPS only, and only to the provider's `api_hosts`. A redirect to another origin raises; same-origin redirects are followed for GET and HEAD only. Timeouts are 5 s connect and 20 s read. Idempotent methods get up to 3 attempts with backoff; POST is never retried. On 401 it refreshes once and retries. A refused refresh sets `expired` (`invalid_grant` or no refresh token) or `error` (other 4xx), wipes the tokens, audits `integration.refresh_failed` (actor null) and sends the owner an `integration_issue` notification. Network errors, 429 and 5xx leave the account unchanged.
- D68. **[H]** Revoking at the provider is best effort and is skipped when the same external account is active for the same user in another lab, because Google revokes the whole grant and would break that lab's connection. The local tokens are wiped either way. A token from a failed connect (wrong account, missing scope) is discarded without a provider revoke for the same reason.
- D69. A user has at most one active account per provider per lab (partial unique constraint). Connecting a different external account while one is active fails with `other_account_connected`, so the user must disconnect first. Reconnecting the same external account reuses its row, so links keep pointing at it. Accounts are never deleted. The owner disconnecting audits `integration.disconnected`. Anyone else (`manage_lab_integrations`: pi, lab_admin) or a lifecycle revoke (actor null) audits `integration.revoked`. `manage_integrations` (own accounts) goes to every lab role, viewers included. **[H]** Confirm viewers may connect accounts. Today an account only reads metadata for links, and a viewer can't create links (`edit_content`).
- D70. **[H]** The Google Picker needs an OAuth access token in the browser. `GET L/integrations/google/picker-token/` (next phase) is the single place a token leaves the server: the requester's own active account only, the access token only (never the refresh token), `Cache-Control: no-store`, scope `drive.file`, lifetime of 1 hour or less. The leak test lists it as the one allowed exception. `ExternalLink` targets use SET_NULL, so deleting a linked item leaves a project-level link rather than silently dropping the pointer.
- D71. **[H]** Every in-app notification is also emailed once, when it is created, sharing the notification's dedupe (`core/notifications.notify`). That covers ethics reminders, retention notices, export notices, task assignment and unassignment, and integration issues. Confirm, or limit email to the first three.
